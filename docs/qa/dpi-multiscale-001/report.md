## 100% 결과

- 시스템/모니터 모두 96 DPI, System Aware 상태 1, 배율 계수 1.0입니다. 물리 화면은 1920×1080, 작업 영역은 `(0, 0, 1920, 1032)`, Tk scaling은 1.3333333333333333입니다. Windows 배율을 수동 변경한 뒤 각 입력 검사와 플레이를 새 Python 프로세스로 시작했습니다.
- 교육창 820×470, 배정창 1000×740, 장비 진단창 640×470, Lab 1060×700px입니다. 별도 캡처의 팝업 5종은 중앙 오차 `(0, 0)px`, 관제실 포함 화면 6종은 모두 작업 영역 안입니다. 정규 제1장 교육·고객·배정·결과창 중앙 배치 8개 판정도 모두 `(0, 0)px`입니다.
- 1px 시험선의 확대 보간 회색 비율은 0%(125% 실험 모드도 0%)입니다. 화면별 경계 선명도 지표는 0.8740~0.9279로, 기존 125%의 0.8561~0.9174와 작은 차이가 있습니다. 글꼴 래스터와 화면 구성도 달라지므로 이 수치만으로 일반적인 가독성 우열을 단정하지 않습니다.
- 정규 제1~5장 321 PASS / 0 FAIL, Lab 실제 입력 집중 76 PASS / 0 FAIL, 목록 실제 휠·키보드 11 PASS / 0 FAIL, 랙 실제 클릭·경계 16 PASS / 0 FAIL입니다. 정규 플레이 입력은 실제 클릭 373회, 휠 12회, 키보드 이벤트 290회입니다(125%: 339 / 14 / 290). 화면에 보이는 양에 따라 필요한 스크롤 횟수가 달라졌습니다.
- 장별 결과 5개와 최종 simulation/runtime 저장은 이전 125% 실행과 같습니다. 새 게임마다 생성되는 `simulation.seed`만 구분하며, 요청 runtime은 한 필드도 제외하지 않고 완전히 일치합니다.
- **관찰 O-100-1:** 기본 창에서 125%의 `tall_mid` 대신 `tall` 랙이 선택됩니다. 큰 GPU 숫자와 전력 문구의 텍스트 경계 상자 접촉이 서버당 한 쌍, 총 4쌍 측정됐습니다. 실제 캡처에서는 행 간격이 좁지만 읽기·클릭은 정상입니다. 경계 상자 접촉 수와 실제 획의 겹침은 구분하며, 이를 새로운 DPI 오류로 단정하지 않습니다. 1280×680에서는 작은 GPU 모듈의 번호/ON 접촉 10쌍(이전 QA에도 있던 디자인), 1000×650에서는 0쌍입니다. 랙 글자의 경계 밖 이탈은 없습니다. 배치·글꼴·시험 기준을 수정하지 않고 측정 차이로 보존합니다.
- 전체 회귀는 1,092개를 실행해 **1,090 PASS / 실패 테스트 2개(하위 판정 4건) / ERROR 0 / skip 0**입니다. 세 해상도 subTest가 같은 테스트 메서드에 속하므로 PASS 수와 실패 판정 수를 단순 합산하지 않습니다. 전체를 통과했다고 표시하지 않습니다.
- 사용자 파일 24개, 기존 artifacts 파일 1,127개, 이전 QA 임시 파일 25개는 진단 종료 후에도 SHA-256이 모두 같습니다. [보호 검증](100/protection.json), [100% 요약](100/summary.json), [전체 회귀](100/full.json), [화면 계측](100/capture.json), [정규 플레이 판정](100/regular-checks.json)에 기록했습니다.

### F-100-1 — 기존 hit-test 전경 환경 문제 재현 (미수정)

실패한 메서드는 `test_multiple_active_rows_scroll_select_and_keep_text_inside_body`(1000×650·1280×680·1366×768의 3개 하위 판정)와 `test_new_tutorial_completes_through_small_window_controls`(1개 판정)입니다. 모두 위젯 위치를 조회하는 `winfo_containing(...)`이 `None`이어서 실패했습니다. 좌표/글자 크기 허용치를 넘은 실패가 아닙니다.

두 테스트를 새 System Aware 프로세스에서 그대로 집중 재현했습니다. 원래 assert를 그대로 실행하고 전경을 바꾸지 않는 관찰 래퍼로, 실패 순간의 중심/하단 좌표 소유자만 기록했습니다. 같은 4건이 재현됐으며 7개 좌표 모두 테스트 프로세스가 아닌 **전경 PID 18412** 소유였습니다. 후속 프로세스 이름 조회 결과는 `Code`(VS Code)였습니다. 즉 다른 프로세스의 전경 창이 검사 좌표를 차지하는 상황을 이번에는 실패 순간에 직접 관측했습니다. [집중 재현 판정](100/hit-test-diagnostic.json), [좌표 소유 기록](100/hit-test-ownership.json).

이전 [dpi-review-001의 간헐적 실패 기록](../dpi-review-001/report.md)에도 같은 두 메서드·같은 `None` 실패가 DPI 비인식 모드에서 재현되어 있습니다. 이번 결과는 해당 기존 환경 문제와 같은 유형으로 분류합니다. 실제 Win32 입력 하네스는 입력마다 전경/소유를 확인하며, 100% 정규 플레이와 Lab·목록·랙 실제 입력은 모두 통과했습니다.

**해결안(미구현):** 테스트의 공통 지원 코드에서 각 hit-test 직전에 해당 테스트 창의 전경·소유를 확보하고 확인합니다. 영향 범위는 `tests/support.py`와 `tests/test_layout_gui.py` 등의 테스트 지원 코드이며 게임 규칙·저장 형식 변경은 필요하지 않습니다. 사용자가 실제 수정 전에 영향과 해결안을 보고하도록 요청했으므로 이번 검증에서는 적용하지 않았습니다. 최초 실패 기록을 보존하며 기대값 수정, 허용 오차 확대, 전경 강제 후 실패값 교체를 하지 않았습니다.

## 150% 결과 — 기본 창 경계 문제 (미수정)

시스템/모니터 모두 144 DPI, System Aware 상태 1, 배율 계수 1.5입니다. 물리 화면은 1920×1080, 작업 영역은 `(0, 0, 1920, 1008)`, Tk scaling은 1.99803343166175입니다.

**F-150-1:** 기본 모드 선택 창에서 목록 검사 Preflight가 작업 표시줄과의 24px 겹침을 감지하여 30초 뒤 중단됐습니다. 실제 입력/플레이 시도는 0회입니다. 전경·클릭 지점 소유는 정상이며 외부 창 간섭과는 구분합니다. `main.py`의 `ModeSelection.__init__`과 `SimulatorApp.__init__`은 `fit_main_window()` 뒤에 `root.minsize(*dpi.size((1000, 650)))`를 적용합니다. 150%에서 높이 975px가 되어 맞춤 높이보다 커지고, 제목줄까지 포함하면 작업 영역을 초과합니다. 캡처의 관제실도 `inside_work_area=false`입니다.

배정창·Lab은 작업 영역 안으로 제한되지만 밀려난 부모 중심과 비교하면 `(0, -22)px`입니다. 이는 팝업이 화면 밖으로 나간 실패와는 다르며, 기본 부모 창의 경계 문제와 함께 기록합니다. 중앙 허용치 ±8px를 늘리지 않습니다.

**해결안(미구현):** 메인 창 최소 크기도 현재 작업 영역과 창틀을 고려한 상한으로 제한합니다. 영향 범위는 모드 선택·관제실 초기 크기/최소 크기와 관련 배치 회귀이며, 게임 규칙·저장 형식 변경은 필요하지 않습니다. 이번 검증에서는 원본 코드를 수정하지 않습니다.

원래 기본 창의 실패 자료를 보존하며 나머지 원본 검사를 실행했습니다. 목록·랙·Lab 집중 검사의 기본 실행은 모두 같은 Preflight 경계 문제로 실제 입력 전에 중단됐습니다. 정규 플레이의 원래 진입점은 같은 코드의 Lab 집중 검사 통과 자료를 요구하므로 기본 조건의 정규 플레이에는 진입하지 않았습니다. 실제 입력과 정규 플레이는 **별도 최대화 준비 조건**으로 추가 검사했습니다. 로컬 실행 래퍼는 원래 Preflight 전 창을 최대화하고 중복 최대화 요청만 멱등 처리합니다. 기존 안전 가드·입력·판정·기대값은 유지합니다. 이 추가 실행이 통과해도 기본 실행을 PASS로 바꾸지 않습니다.

최대화 조건의 목록 실제 휠·키보드 11 PASS, Lab 실제 입력 집중 76 PASS, 정규 제1~5장 321 PASS / 각각 0 FAIL입니다. 정규 플레이는 실제 클릭 412회·휠 14회·키보드 이벤트 290회입니다. 제1장 주요 팝업 중앙 판정 8개는 `(0, -1)`~`(0, +1)px`입니다. 장별 결과 5개·최종 simulation(새 게임 seed 제외)·runtime 전체가 이전 125% 결과와 같습니다.

최대화 랙의 A~D 실제 클릭·선택·Inspector·테두리 4개와 글자 경계 1개 및 저장 보존 1개, 총 6개 판정은 통과했습니다. 그러나 다음 1280×680 설계 크기(실제 클라이언트 1920×1020px)에서는 작업 표시줄 가림으로 중단됐으므로 전체 랙 검사는 완료 PASS가 아닙니다. 1000×650 단계에는 도달하지 않았습니다. 처음 최대화 상태에서는 `compact` 랙·텍스트 경계 상자 접촉 10쌍·경계 밖 글자 0개입니다. 정규 플레이/Lab은 끝까지 통과했지만, 이 추가 실행만으로 150% 전체 화면 사용성을 승인하지 않습니다.

### 실제 크기와 기존 125% 비교

값은 클라이언트의 실제 물리 px입니다. 125%는 이전 검증 자료이고 100%·150%는 이번 새 프로세스 계측입니다.

| 화면 | 100% / 96 DPI | 기존 125% / 120 DPI | 150% / 144 DPI |
| --- | ---: | ---: | ---: |
| 교육창 | 820×470 | 1025×588 | 1230×705 |
| 관제실 | 1280×860 | 1600×951 | 1872×975 |
| 배정창 | 1000×740 | 1250×925 | 1500×912 |
| 장비 진단 | 640×470 | 800×588 | 960×705 |
| 결과 카드 | 560×334 | 700×412 | 840×495 |
| Lab | 1060×700 | 1325×875 | 1590×912 |

150% 관제실은 하단 일부가 작업 표시줄에 가립니다. 나머지 캡처 팝업 5종은 작업 영역 안입니다. 150% 배정창·Lab의 높이는 작업 영역에 맞춰 줄어들어 본문 스크롤이 필요하며 고정 하단 버튼은 보입니다. 그 외 팝업 중앙 오차는 `(0, 0)px`입니다. 100%와 기존 125%의 캡처 팝업 중앙 오차는 모두 `(0, 0)px`입니다.

1px 시험선의 확대 보간 회색 비율은 세 배율 모두 0%입니다. 150% 화면별 경계 선명도 지표는 0.8457~0.9082입니다. 100%·125%·150%는 서로 다른 글꼴 래스터/화면 크기이므로 이 지표로 선명도 순위를 단정하지 않습니다. 캡처에서 글자는 비트맵 확대 흐림 없이 읽히며, 150%의 실제 하단 잘림·부모 중심 제한은 별도 실패로 기록합니다.

최대화 준비 조건 재현은 저장소 루트에서 `C:\anaconda3\python.exe artifacts/dpi-multiscale-001/run_maximized.py tests/qa/autoplay_chapter5.py --focus <새 출력 폴더>`로 실행할 수 있습니다. 실험 DPI 설정을 Tk 생성 전에 적용하며 Windows 배율을 바꾸지 않습니다. [준비 조건과 도구 원문](maximized-fixture.md)에 재현 절차를 기록했습니다. Python 실행 도구는 로컬 산출물에 보존하며 커밋에는 문서만 포함합니다.
