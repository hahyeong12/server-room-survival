위 HWND는 **이 실행의 게임 자체 핸들**입니다. 외부 창 HWND·제목·프로세스명·사용자 경로는 공개하지 않았습니다. 핸들 숫자는 실행마다 달라질 수 있습니다.

사용자에게 수동 활성화 준비 여부를 물었고 “지금 준비됐습니다”라는 답변 뒤 실행했습니다. 다음 문구와 작업 표시줄/Alt+Tab의 QA 준비 창을 안내했습니다.

> 게임 창이 다른 창 뒤에 있습니다. 게임 창을 한 번 직접 활성화해 주세요. 이후 자동 플레이가 시작되면 마우스와 키보드를 사용하지 마세요.

이번에는 **첫 표본부터 전경 조건이 충족**되어 30초 대기나 재안내 경로에는 들어가지 않았습니다. 사용자가 정확히 어떤 동작으로 창을 활성화했는지는 하네스가 추적하지 않습니다. 사용자 준비·수동 활성화 안내·HWND 검증을 포함한 이번 실행 조건에서 전경 문제가 해소된 것은 확인했지만, 특정 코드 변경만으로 모든 환경의 자동 전경 전환 문제가 해결됐다고 주장하지 않습니다.

### story-002와 달라진 점

- 이전의 `lift()`/`focus_force()` 시도를 제거했습니다. 전경을 강제로 바꾸는 API, 외부 앱 최소화/종료, 외부 앱 자동 클릭은 사용하지 않습니다.
- HWND를 반환·인수로 쓰는 Win32 함수에 포인터 폭을 명시했습니다. 실제 클라이언트/프레임/ancestor 핸들을 대조하고 자기 프로세스 창임을 확인합니다. **이 예방 보완이 이전 실패의 원인이었다고 입증한 것은 아닙니다.** story-002에는 비교할 실제 HWND 기록이 없습니다.
- 캡처 보정 뒤에 최대 30초의 준비 단계를 두었습니다. 실패하면 시나리오를 호출하기 전에 중단하고 `play_attempts=0`으로 기록합니다. 성공한 이번 결과는 `play_attempts=1`입니다.
- Preflight의 30초는 안정 확인·카운트다운을 포함한 상한입니다. 실제 시간 초과·전경 상실 시 초기화 경로는 self-check의 합성 시간으로 확인했으며, 이번 실제 데스크톱에서는 발생하지 않았습니다.
- 외부 가림 때문에 같은 전체 플레이를 반복하지 않았습니다. 이번 GUI 실행·Preflight·실제 플레이는 각각 1회입니다.

별도 사용자 PowerShell에서 실행하는 대안도 검토했습니다. 아래 명령을 저장소 폴더의 별도 PowerShell에서 실행하면 같은 Preflight를 사용합니다. 이번에는 현재 실행 경로가 통과하여 별도 PowerShell 실행은 하지 않았습니다.

```text
python tests/qa/autoplay_story_ch1.py <새 출력 디렉터리>
python tests/qa/autoplay_story_ch1.py --self-check
```

현재 노트북에서는 설치된 Anaconda Python을 명시해 실행했습니다. 새 의존성이나 별도 자동화 시스템은 설치하지 않았습니다.

- 각 완료 직후 임시 DB의 runtime 성공·onboarding 완료 이력을 읽기 전용으로 확인했습니다. 제1장 시작 체크포인트는 매 고객 완료 뒤에도 최초 SHA-256과 같았습니다.

- 최종 평균 점수는 **100.0점**, 세 고객 모두 기한 내 완료입니다. **누적 반환 GPU 16개·전력 17단위**는 순차 업무 합계이며, 동시 총용량을 뜻하지 않습니다. 실제 마지막 가용량은 GPU 10·전력 10입니다.
- 성공 결과창의 MISSION SUCCESS·3/3·세 고객 점수·다음 근무 안내를 확인했습니다. **[제2장 — 한정된 자원 · 시작] 버튼이 활성 상태**였습니다. 안내까지 스크롤했지만 버튼은 누르지 않았습니다.

### 이전 QA 오탐과 구분

- **요청서 파서:** story-001의 숫자/단위 분리 오류는 이번 SG·JP·US GUI 검사 **3/3 통과**로 확인했습니다.
- **배정창 설명 가려짐:** 세 고객 모두 기본 위치에서 설명 라벨이 숨겨져 있었지만, 실제 스크롤바 아래 화살표 **2클릭** 뒤 보였습니다. 다시 위 화살표 2클릭으로 복귀했습니다. 세 번 모두 접근 가능하므로 **접근 불가능한 라벨이라는 버그로 판정하지 않았습니다**. 원시 스크롤 후보와 이동 이력은 JSON에 보존했습니다.
- **금색 강조:** 스토리 첫 근무에서는 설계상 비활성이고, 단계·고객별 목표 카드가 정상 전환됐습니다. 튜토리얼처럼 금색이 없다는 이유로 FAIL 처리하지 않았습니다.
- 검사 실패를 없애려고 숨겨진 신규 고객 행을 PASS로 바꾸지 않았습니다. 스크립트의 비정상 종료 코드는 위 UI 검사 3건을 반영합니다.
