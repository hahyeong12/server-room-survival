# QA ui-consistency-001 — 제1~4장 QA 후속 화면 정합성 정비

**제4장 QA(chapter4-001)에서 관측한 화면 표현 문제 3건을 고쳤습니다.** 장비 진단창·대응 카드의 장 번호를 `제4장`으로 통일했고, 장비 FAULT·복구·작업 이전 준비 중에 초록 '정상 실행 중' 배지가 뜨지 않게 했으며, 작업 이전 결과 카드가 준비 10분이 끝난 뒤가 아니라 **이전 확정 직후** 뜨도록 했습니다. 게임 엔진의 시간·작업량·장애·자원 원장·점수·기한·고객 동의 규칙과 저장 형식(SQL·JSON 필드)은 바꾸지 않았습니다. 제5장·Engineering Lab은 시작하지 않았습니다.

### P0-2 장비 장애 중 '정상 실행 중' 배지

- **원인:** 장비 장애는 네트워크 단계(`state.phase`)와 독립이라 FAULT·REPAIRING·이전 준비 중에도 작업이 `running`으로 남습니다. 하단 배지 색은 `status_tone()`이 단계만 보고 정해 초록 ●이었고, 문구는 `정상 실행 중 · 서버 장애 A …`처럼 이어 붙였습니다. 진행 목록은 REPAIRING에도 '서버 장애'라고 표시했습니다.
- **수정:** 조회 전용 `aidc/ui/job_status.py`의 `job_status(session, run)` 하나가 서버 원장·장비 상태·이전 준비 시간으로 상태를 판정하고, 하단 배지·진행 목록·요청함·Inspector·제4장 카드 '현재 상태'가 같은 결과를 씁니다. `session.hardware_status()`(지연 안내 문구)도 REPAIRING을 '장비 복구 중'으로 구분합니다. 엔진 상태는 읽기만 합니다.

### P0-3 작업 이전 결과 카드 표시 시점

- **원인:** 결과 카드는 `show_story_event()`가 띄우는데, 고객 요청·배정 창이 열려 있으면 보류했다가 그 창이 닫힐 때(`story_work_window_closed`) 다시 확인합니다. 배정창(`open_allocation_plans`)은 이 종료 콜백을 연결했지만 **이전 계획 창(`open_migration_plans`)은 연결하지 않았습니다.** 그래서 이전을 확정하는 순간에는 창이 아직 열려 있어 카드가 보류됐고, 창이 닫혀도 다시 확인하지 않아 다음 세션 행동(+10분, 준비 종료 시점)에서야 카드가 떴습니다. 장비 복구는 창 없이 바로 실행돼 문제가 없었습니다.
- **수정:** 이전 계획 창도 `build_popup`으로 만들고, 스토리에서 `<Destroy>`를 `story_work_window_closed`에 연결했습니다. 카드 행은 **선택 당시 기록**(`선택 당시 결과`, `선택 시 예상 완료`)과 **현재 판정**(`현재 상태`)으로 나눠, 나중에 [장애 결과 보기]로 다시 열어도 남은 준비 시간을 오해하지 않게 했습니다.
- **중복·이어하기:** 카드 확인 키(`<요청>:migrate:1`)와 `feedback_seen` 저장은 그대로라 한 번만 뜨고, 시간 진행·저장 후 재개 때 다시 뜨지 않습니다(Tk 테스트). 시간은 +10분 한 번만 진행됩니다.

| | 수정 전(chapter4-001 정규·집중 실행 모두) | 수정 후(이번 네이티브 집중 실행) |
| --- | --- | --- |
| A 이전 카드가 기록된 단계 | `제4장 미션 A 준비·재개·완료`(준비 종료 15:00 뒤) | `제4장 미션 A 장비 장애·진단`(확정 직후, 연습 시계 09:30, 준비 10분 남음) |
| B 복구 카드 | `장비 장애·진단` | `장비 장애·진단`(기존 동작 유지) |

**재개 후 발견·보완:** 첫 네이티브 집중 실행([attempt-1 원본](native-focus-attempt-1.json))에서 '현재 상태' 행이 늘어 카드가 고정 높이 330px를 넘었고, [업무로 돌아가기]가 [창 아래로 잘린 것](screenshots/attempt1_card_clipped.png)을 하네스가 '보이지 않는 버튼'으로 감지해 **안전 중단**했습니다(판정 16 PASS / 0 FAIL, 게임 실패 아님). 이번 변경으로 생긴 문제이므로 카드 문구를 짧은 한 줄(`brief`)로 줄이고, 카드 높이를 실제 요구 높이 이상으로 잡게 했습니다. 버튼이 창 안에 있는지 Tk 테스트에 추가했습니다.

## 4. 미해결: 교육창 첫 등장 흰 프레임

이번에는 **원인 메커니즘을 실측으로 좁혔지만 효과가 입증된 수정은 없어 코드를 바꾸지 않았습니다.** 계측 스크립트: [flash_probe.py](flash_probe.py)(메모리 DB, 독립 연습으로 제2·3장 시작 직후 교육창 첫 등장).

| 측정 시점 | 흰 비율(클라이언트 영역, 밝기>235) |
| --- | --- |
| `center_dialog()`의 deiconify 직후(동기) | 0.0 — 아직 화면 합성 전이라 뒤 화면이 보임 |
| 생성자 나머지 작업 뒤·이벤트 루프 전 | **0.87~1.0**(5회 중 3회는 0.0으로 아직 합성 전). [실제 프레임: 전부 흰 창](screenshots/probe_before_loop_white.png) |
| `root.update()` 뒤 | 0.007 — [정상 그려짐](screenshots/probe_after_loop_painted.png) |

- **확인된 사실:** Tk는 Windows의 그리기 요청을 이벤트 루프에서만 처리합니다. 교육창은 `withdraw → 구성 → 배치 → deiconify` 순서로 표시된 뒤, 이벤트 루프가 창을 그릴 때까지 칠해지지 않은 흰 상태로 보입니다. QA에서 본 '부분 흰 사각형'은 일부 자식 위젯만 그려진 중간 상태와 같은 모양입니다.
- **시도한 완화(모두 채택하지 않음):** Win32 `RedrawWindow(UPDATENOW)` 강제 그리기 — 효과 없음(1.0×3). 투명도 0으로 표시 후 복원 — 효과 없음(1.0×3). 표시 직후 창 이벤트만 처리(`dooneevent(WINDOW_EVENTS)`, 타이머 미실행) — 생성자 끝에서는 0.007이 됐지만 **마지막 흰 프레임까지의 시간**은 수정 전 1.17~1.76초 → 0.88~1.39초로 측정 잡음 범위 안이었습니다. 흰 시간이 줄지 않고 앞당겨졌을 뿐이라 되돌렸습니다.
- **가설:** 장 시작 시 관제실 전체를 새로 만들면서 쌓인 배치·그리기 이벤트가 큐에서 먼저 처리되고, 그 뒤에야 교육창이 그려집니다. 따라서 흰 시간은 교육창 자체보다 **관제실 재구성 직후 창을 바로 보여 주는 순서**에 좌우되는 것으로 보입니다.
- **후속 후보(미구현):** 관제실 첫 그리기가 끝난 뒤(예: `after_idle` 연쇄 또는 관제실 `<Map>`/`<Expose>` 이후) 교육창을 표시하는 순서 변경. 표시 시점을 바꾸면 기존 배치 측정(`dialog.placement`)·GUI 테스트 기대값에 영향이 있어 별도 검증이 필요합니다.
- 이번 네이티브 실행에서도 제4장 연습 브리핑 첫 등장 t=7.967초에 흰 비율 0.552 후보를 관측했습니다([프레임](screenshots/white_frame_ch4_briefing.png)). 진행을 막지 않았습니다.

## 5. 미해결: 125% DPI 흐림 (이번에 변경하지 않음)

| 항목 | 확인 내용 |
| --- | --- |
| 현재 동작 | 게임 코드에 DPI 인식 설정(`SetProcessDpiAwareness` 등)이 없습니다. QA 기록의 `dpi_awareness=0`(DPI 비인식), `tk scaling≈1.335`, 캡처 배율 1.25가 이를 뒷받침합니다. Windows가 96DPI로 그린 창을 125%로 **비트맵 확대**하므로 흐립니다 |
| 바꾸면 영향 받는 곳 | ① 고정 픽셀 크기: 관제실 1280×860, 교육창 820×470, 진단창 600×340·640×470, 카드 560×330, Canvas GPU 모듈·랙·초상화, `wraplength` ② 글꼴은 포인트 단위라 실제 DPI로 커지지만 픽셀 레이아웃은 그대로라 칸이 좁아짐(잘림·줄바꿈 변화) ③ `window_placement`의 작업 영역·창틀 오프셋·음수 좌표 보정(물리 좌표로 바뀜) ④ QA 하네스의 논리↔물리 좌표 변환·클릭 좌표·흰 비율 계측 ⑤ 해상도 3종 배치를 검사하는 기존 GUI 테스트 |
| 100% 환경 | 비인식/인식 모두 배율 1이라 차이가 거의 없음(회귀 위험 낮음) |
| 125% 환경 | 선명해지지만 ①~⑤를 다시 맞춰야 함. 픽셀 상수를 `tk scaling` 비율로 곱하는 공통 함수가 선행 조건 |
| 권장 순서(제안) | (1) 픽셀 상수를 한곳에 모아 배율 함수로 감싸기 → (2) 실험 플래그로만 Per-Monitor DPI 인식 켜기 → (3) 100%/125%/150%에서 관제실·교육창·배정창·진단창 실제 캡처 비교 → (4) QA 하네스 좌표 변환 갱신 → (5) 기본값 전환 여부는 사용자 결정 |

## 6. 교육 설계 의견 — 제4장 힌트의 강도 (변경하지 않음, 별도 협의)

제4장 QA에서 진단창의 `· 기한 내 / · 기한 초과`(`chapter3b.diagnosis_rows`의 `_flag`)와 이전 불가 시 `Server A를 복구하면 … 재개할 수 있습니다`(`session.hardware_diagnosis`의 `advice`)가 정답을 강하게 드러낸다는 의견이 있었습니다. **이번 작업에서는 안내를 삭제하거나 난이도를 올리지 않았습니다.**

**현재 단계(제1~4장)에서 힌트가 필요한 이유**
- 제1~4장은 [학습 설계](../../LEARNING_DESIGN.md)의 L0 관찰 단계입니다. 목표는 "장비 장애와 네트워크 장애는 다르다", "복구는 시간을, 이전은 자원을 쓴다", "작업은 전체를 한 번에 옮겨야 한다"는 **개념 구분**이지 계산 숙련이 아닙니다.
- 예상 시각과 기한을 직접 빼 보지 않아도 결과(A의 5분 차이)를 바로 비교할 수 있어야 선택→결과의 인과를 배웁니다. 계산 실수로 장 전체를 실패하면 개념 학습보다 좌절이 커집니다.
- 진단창을 열어야만 복구/이전 버튼이 풀리므로, 힌트는 이미 "관찰한 뒤에만 보이는 근거" 자리에 있습니다.

**제5장 이후 점진적으로 줄이는 방법(제안)**
1. 결론 표시 → 근거 표시: `기한 내/초과` 대신 예상 시각과 기한만 나란히 두고 비교는 학습자가 합니다.
2. 권고 문장 제거 → 사실 문장 유지: "정상 GPU 6 < 필요 7 · 전체 이전 불가"는 남기고 "복구하면 재개할 수 있습니다"는 뺍니다.
3. 표 → 조회 행동: 정상 서버 여유량을 미리 합산하지 않고 Inspector·명령(L1~L3)으로 직접 확인하게 합니다.
4. 사후 피드백 강화: 선택 전 도움을 줄인 만큼 결과 카드에서 '선택 당시 근거 / 실제 결과'를 비교해 회고를 돕습니다(이번에 나눈 `선택 당시 결과`/`현재 상태`가 바탕이 됩니다).
5. 연습·반복 도전에서만 도움 단계를 고를 수 있게 하고, 정규 진급 평가는 낮은 도움 단계로 고정합니다.

**정답 노출과 판단 근거 제공을 구분하는 기준(제안)**

| 구분 | 판단 근거 제공(유지 가능) | 정답 노출(높은 단계에서 줄일 대상) |
| --- | --- | --- |
| 형태 | 관측값·제약·시간을 사실로 제시 | 비교·결론·권고를 대신 계산해 제시 |
| 예 | "복구 예상 15:40, 기한 15:35", "정상 GPU 6 / 필요 7" | "기한 초과", "복구하면 재개할 수 있습니다", 추천 배지 |
| 점검 질문 | 이 문장을 지워도 학습자가 같은 결론을 스스로 낼 수 있는가? | 이 문장 하나만 읽고 버튼을 고를 수 있는가? |
| 시점 | 관찰 행동 뒤에 보임 | 관찰 없이도 보임 |
