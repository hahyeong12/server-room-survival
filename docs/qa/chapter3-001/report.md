## 전체 실행 전 집중 검사와 QA 보완

전체 플레이는 **1회뿐**입니다. 다음 집중 검사는 전체 플레이 횟수에 포함하지 않습니다.

1. 기존 제3장 Tk 집중 검사에서 진단 전 대응 잠금·잘못된 대응·복구 준비·실패 후속 처리 연결을 확인했습니다. 결과창 테스트가 구형 `free/status/review` 버튼을 기대해 1회 오류가 났고, 현재 결과창의 `retry/modes` 기대값으로 보완했습니다. 이어 메뉴 테스트의 구형 기대값에서 `chapters`가 빠진 1회 실패도 수정했습니다. **게임 UI를 과거 테스트에 맞춰 바꾸지 않았습니다.**
2. 새 QA의 제3장 입력 흐름을 독립 임시 **연습 fixture**로 검사했습니다. 첫 집중 실행은 연습 슬롯에도 정규 체크포인트가 있다고 가정한 QA의 `FileNotFoundError`로 **마우스 클릭 전에 중단**됐습니다. 연습은 체크포인트를 만들지 않는 정상 차이를 명시적으로 구분했습니다. 이 중단은 게임 미션 실패가 아닙니다.
3. 두 번째 집중 실행은 같은 제3장 QA 함수로 실제 요청·배정·진단창·대응·10분 준비·정상 완료·결과 버튼까지 **38 PASS / 0 FAIL**, 49클릭·휠2회로 통과했습니다. [focus.json](focus.json)의 `kind=chapter3_focused_fixture`, `practice=true`, `full_play_attempts=0`입니다. 여기서는 제1·2장 정규 진행을 증명하지 않습니다.
4. 집중 검사와 **같은 QA 소스 SHA-256**일 때만 정규 실행을 허용하도록 했습니다. 이후 새 임시 정규 슬롯에서 검증된 제1·2장 코드를 재사용하고 두 결과창의 실제 시작 버튼을 눌렀습니다. 연습 fixture나 엔진 호출로 정규 해제를 우회하지 않았습니다.

정규 플레이의 대응 선택은 고객 ID·미션 순서·엔진의 `incident_kind`를 사용하지 않습니다. **실제 진단창을 연 후 표시된 주 경로 상태·필요/가용 대역폭·백업 설명을 읽어 판단**하며, 증거가 두 판단 규칙에 맞지 않으면 중단합니다. 예상 시나리오와 실제 화면의 일치는 별도로 검사합니다.

## 제1·2장 재완주 및 정규 진입

제1장 싱가포르→일본→미국을 각각 고성능30분·100점·기한 내 완료했고, 매번 자원이 전량 반환됐습니다. [제1장 결과](screenshots/ch1_success.png)의 실제 제2장 시작 버튼으로 같은 슬롯에서 진급했습니다.

제2장은 일본 고성능4/5와 원래 허용된 미국 절약형4/3을 **10:30 동시 시작**했습니다. 일본은11:10·100점, 미국은12:10·95점·기한 정시에 완료했고 종합97.5점입니다. 부분 반환과 최종 가용10/10도 재확인했습니다. [제2장 결과](screenshots/ch2_success.png)의 **[제3장 — 끊어진 연결 · 시작]**을 실제 클릭해 정규 제3장에 진입했습니다. 제3장 시작 체크포인트가 생성됐으며 완료 후에도 해시가 같았습니다.

- **125% DPI 흐림 유지:** 기존 배율의 텍스트/선 흐림은 남아 있으며 DPI 인식이나 전체 UI를 바꾸지 않았습니다. 실제 진단표는 두 미션 모두 핵심 수치·백업 설명·하단 버튼이 창 안에서 보였고, 미국의 ‘같은 병목 공유’는 두 줄로 표시됐습니다.

## AI의 교육·게임성 평가

다음은 실제 캡처·표시 문구에 대한 **AI의 주관적 의견**입니다. 기능 assertion 및 사람 대상 학습 효과 검증과 구분합니다.

| 증거만으로 추론 가능한가 | A는 백업6이 필요5를 수용하고, B는 백업도 같은 병목이어서 서로 다른 선택을 설명할 수 있습니다. 이번 자동화도 화면 셀로만 판단했습니다. 다만 압축이 필요 대역폭을 얼마나 줄이는지 진단표 자체에는 나오지 않아, 정확한 효과량의 사전 예측까지 지원한다고 보기는 어렵습니다 |
| 선배의 정답 노출 | 실제 브리핑과 장애 안내는 연결·필요량·백업·장비를 확인하라고 하며 조치명을 정답으로 제시하지 않았습니다. 진단 뒤에도 수치로 판단하라고 했고, 구체적인 우회/압축의 이유는 실제 대응 결과 카드에 나왔습니다 |

| 상태의 일관성 | 네트워크 문제 동안 GPU·서버는 정상이고 점유를 유지했습니다. ‘복구 성공’ 카드에 ‘복구 준비10분’이 함께 나와 즉시 실행과 구분됩니다. A의 주 경로가 DOWN인 채 백업으로 정상 전송하는 점도 기록과 맞습니다 |
| 제2장 대비 독립 판단 | 제2장의 ‘다른 고객 배정 가능’ 추천과 달리, 진단창은 관측값을 보여 주고 조치 버튼의 정답 추천은 하지 않습니다. A에서 통한 우회를 B에서도 누르는 습관을 ‘같은 병목’이 막아, 원인 비교와 가설 변경을 요구합니다. 자원 배정의 추천은 여전히 남아 있습니다 |
| 실제 원리와 단순화 | 연결 단절과 용량 부족의 차이, 우회가 병목을 공유하면 효과가 없다는 설명은 원인 비교에 유용합니다. 브리핑과 결과 카드의 ‘교육용 구성’ 표기도 확인했습니다. 압축의 고정2단위 감소·우회 효과·10분 준비·3회/60분 제한은 이 게임 규칙이며 실제 네트워크의 일반 보장으로 가르쳐서는 안 됩니다 |
| 개선 의견 | 향후에는 A/B의 주 경로·병목 위치를 같은 작은 구조도로 비교하거나, 결과에서 대응 전후 ‘필요/가용’ 두 쌍을 나란히 보여 주면 수치 변화가 더 잘 남을 것 같습니다. 조치를 고르기 전 예상 이유를 적게 하는 방식도 검토할 수 있습니다. **이번에는 구현하지 않았습니다** |
