## 정규 실행 전 집중 검사

전체 정규 플레이는 **1회**입니다. 아래 fixture와 Tk 단위 검사를 정규 제1→4장 완주 실적으로 세지 않습니다.

- 기존 `tests.test_chapter3_gui.Chapter3bGuiTests` **3 PASS**: 제4장 표시·수동 장애 차단·장비 진단 전 복구/이전 잠금·진단 후 해제·복구 버튼 연결·연습 메뉴. 메모리/임시 DB의 `.invoke()` 검사입니다.
- 첫 네이티브 집중 실행은 독립 제4장 **연습 fixture**에서 두 고객 모두 기한 내 완료했으나, 최종 QA 비교 **47 PASS / 1 FAIL**이었습니다. QA가 연습 슬롯에서도 제5장 정규 시작 버튼이 활성화돼야 한다고 잘못 기대했습니다. 실제 게임은 `training_unlock_reason()`으로 연습의 정규 진급을 차단하며 이는 기존 정책입니다. **게임 미션 실패나 입력 실패가 아닙니다.** [focus-attempt-1.json](focus-attempt-1.json) 원본을 보존했습니다.
- 정규/연습의 진급 기대값만 구분하고 재검사했습니다. 두 번째 집중 실행 **48 PASS / 0 FAIL**, 51클릭·휠2회·약73초입니다. [focus.json](focus.json)의 `kind=chapter4_focused_fixture`, `practice=true`, `full_play_attempts=0`을 명시했습니다. 이 fixture의 직접 연습 초기화는 QA 입력 흐름 검사에만 사용했습니다.
- 집중 검사 통과 JSON과 **QA 본체 및 재사용하는 제1·2·3장 소스 해시가 같아야** 정규 실행을 허용합니다. 실행 디렉터리에 독점 `attempt.json`을 생성해 같은 디렉터리를 덮어 실행하지 않습니다. 예상 밖의 진단이나 기한 내 대응이 없으면 중단합니다.

첫 QA 실패를 성공으로 고치거나 assertion을 삭제하지 않았습니다. 정규와 연습의 실제 차이를 각각 검증하며, 원본 JSON의 `completed=true`는 두 미션의 완료를 뜻합니다. 첫 집중 실행의 `failed=1`을 함께 봐야 하며 전체 QA 통과로 해석하지 않습니다. 추가 정규 플레이는 하지 않았습니다.

## 실제 진단값과 선택 이유

두 미션 모두 작업60 중 **30·50%**에서 Server A 장비 장애가 발생했습니다. 작업 중단 뒤 GPU/전력 점유를 유지했고 네트워크 경고는0, `incident_kind=None`이었습니다. 장비 진단 전에는 복구·이전 버튼이 모두 비활성화됐으며, **실제 진단창을 연 뒤에만** 선택했습니다. 핵심 진단 행·기한·B의 불가 사유는 스크롤 없이 전부 보였고 가시성 검사도 통과했습니다.

선택 함수는 미션 ID/순서를 보지 않습니다. **실제 화면의 이전 가능 여부·필요/정상 자원·예상 시각·기한**을 읽어 이전이 가능하고 더 빠르게 기한을 지킬 수 있으면 이전을, 이전 불가 사유가 있고 복구가 기한 내이면 복구를 선택했습니다. 진단값이 판단 규칙을 만족하지 않으면 성공을 강행하지 않습니다.

[읽기 전용 사후 대조](evidence-check.json)에서도 실제 정상 서버 B/C/D의 원장·용량과 표시6/6, 작업 필요3/4·7/7, 예상 시각/기한 관계가 일치했습니다. 이 대조는 저장된 실제 실행 결과를 읽었으며 게임 상태를 변경하거나 플레이를 추가하지 않았습니다.

**B에서 진단의6/6과 관제실의 현재 빈3/3은 계산 대상이 다릅니다.** 관제실은 현재 빈 정상 자원만 보여 줍니다. 진단의 전체 재배치 계산은 해당 작업을 제외한 투영 원장을 사용해 현재 작업이 정상 B/C에서 쓰는 GPU3/전력3도 다시 사용할 수 있는 자원에 포함합니다. 그래도 전체7/7을 수용할6/6만 있으므로 이전할 수 없습니다. 장애 A의 조각4/4만 옮기는 계획이 아닙니다.
