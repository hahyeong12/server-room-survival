## 2. 교육창 흰 프레임

### 측정 방법

이전 [flash_probe.py](../ui-consistency-001/flash_probe.py)는 게임과 같은 프로세스에서 `sleep`과 화면 캡처 스레드를 함께 돌렸습니다. 그래서 이벤트 루프와 GIL이 막혀 측정값(1초 이상)이 부풀 수 있었습니다. 이번에는 [tests/qa/flash_bench.py](../../../tests/qa/flash_bench.py)를 새로 만들었습니다.

- **게임(자식 프로세스):** 실제 모드 메뉴(`ModeSelection`)를 띄우고 `mainloop`를 그대로 돌립니다. 메뉴가 그려진 뒤 메뉴 버튼과 같은 호출로 장을 시작합니다. 메모리/임시 DB만 씁니다.
  - `ch2`: 제2장 연습 시작
  - `ch3b`: 제4장 연습 시작
  - `next2`: 제1장 결과창에서 [제2장 시작]과 같은 `begin_chapter2()`
- **관측(부모 프로세스):** 교육창 HWND를 찾고 GDI `StretchBlt`로 약 17ms 간격으로 클라이언트 영역을 캡처합니다. 흰 비율(밝기>235)과 최종 화면과의 차이를 계산합니다. `SendMessageTimeout(WM_NULL)`로 창이 메시지에 다시 응답한 시각(입력 가능 시점)을 잽니다. 두 프로세스는 같은 QPC 시계를 씁니다.
- `ch3`은 측정하지 않았고, `training`(제5장 시작)은 교육창(현장 교육)을 띄우지 않아 대상에서 뺐습니다.

### 확인한 원인

캡처 프레임 순서는 다음과 같았습니다.

1. 아직 합성 전이라 뒤쪽 관제실이 보임
2. Windows 창 열림 애니메이션(반투명) 시작
3. **자식 위젯 자리가 흰 사각형인 프레임**
4. 정상 화면

흰 프레임은 **Windows가 창 합성(애니메이션)을 시작하는 시점이 교육창의 첫 그리기(Expose)보다 빠를 때**만 나타납니다. 그래서 가끔만 보였습니다. 이 경쟁을 좌우한 것은 표시(deiconify) 후 첫 그리기까지의 지연(약 115~230ms)이었습니다.

이 지연은 두 부분으로 나뉩니다.
- 교육창을 띄운 콜백의 남은 작업(대화 기록 저장·강조 갱신 등, 약 55~85ms)
- 장 시작 때 관제실 재구성으로 쌓인 그리기 이벤트(약 50~130ms)

과제의 가설("관제실 첫 그리기가 끝나기 전에 교육창을 보여 줘서 생긴다")은 **부분적으로 맞았습니다.** 결과창에서 다음 장으로 넘어가는 경로(관제실을 다시 만들지 않음)에서도 같은 지연과 흰 프레임이 있었기 때문에, 콜백의 남은 작업도 원인입니다.

### 실험

| 실험 | 내용 | 결과 | 처리 |
| --- | --- | --- | --- |
| 1-last | 숨긴 채 완성·기록 후 콜백 끝에서 표시 | 그리기 전 노출 105~155ms, 흰 캡처 1/30 | 효과 불충분, 미채택 |

### 채택한 수정

`e8d1804`, [main.py](../../../main.py)·[story_dialog.py](../../../story_dialog.py):

- `show_story_help()`는 교육창을 숨긴 채(`show=False`) 만들고, 대화 기록을 저장한 뒤, `after_idle → after(0)`로 `show_window()`를 예약합니다.
- 창 객체는 즉시 생기므로 `story_window` 상태, 중복 방지, 저장 실패 시 닫기는 그대로입니다.
- `StoryDialogueDialog(show=True)`가 기본값이라 복습창 등 다른 호출은 기존처럼 즉시 표시됩니다.
- 예약된 표시 전에 창이나 앱이 닫히면 아무것도 하지 않습니다.

### 실험 중 발생한 오류와 처리

첫 실험 코드는 창 표시 메서드를 `reveal()`, 속성을 `revealed`로 만들었습니다. 이 이름이 부모 `MessageDialog.reveal()`(현재 페이지 글 전체 표시, `self.shown` 사용)을 덮어썼습니다.

부모 생성자가 `render()`를 거쳐 `self.reveal()`을 부르는 시점에는 자식의 `self.revealed`가 아직 없어서, 모든 교육창 생성이 다음 오류로 실패했습니다.

`AttributeError: 'StoryDialogueDialog' object has no attribute 'revealed'`

traceback: `story_dialog.py:16 → ui.py:122 → story_dialog.py:59 → ui.py:188 → story_dialog.py:52`.

측정 도구가 회차마다 게임을 다시 띄우는 구조여서 오류창이 반복됐습니다. 처리 순서는 다음과 같습니다.
1. 측정 프로세스를 종료했습니다.
2. 실험 변경을 되돌렸습니다(두 파일이 `746f3c5`와 같음 확인).
3. 교육창·튜토리얼·복습창 집중 검사 112개를 통과시켰습니다.
4. 원인을 보고했습니다.
5. 겹치지 않는 이름(`show_window`, `window_shown`)으로 다시 실험했습니다.

이 오류를 막는 회귀 테스트를 추가했습니다(`test_dialog_class_keeps_message_text_reveal`).

## 5. 남은 문제

- **흰 프레임:** 측정 범위(세 경로, 이 PC의 125% 배율)에서 0/45가 되었지만, 다른 배율·모니터·느린 PC·다른 창(고객 메신저·배정창·결과창·피드백 카드)의 첫 표시는 측정하지 않았고 바꾸지 않았습니다. 같은 방식을 다른 창에 넓히는 것은 별도 검토 대상입니다.
- **표시 지연:** 교육창이 최대 약 0.14초 늦게 나타납니다. 체감 문제가 있으면 다시 조정할 수 있습니다.
- **125% DPI 흐림:** 변경하지 않았습니다([ui-consistency-001](../ui-consistency-001/report.md) 5절 영향 범위 그대로).
- **교육 UX:** 제5장 Stage 5가 이미 경험한 사건의 시연이라는 한계([chapter5-001](../chapter5-001/report.md))는 그대로입니다. 새 장애·Stage는 범위 밖입니다.
- 정규 전체 네이티브 자동 플레이는 이번에 다시 하지 않았습니다(교육창 표시 경로는 위 실제 Tk 회귀와 측정으로 확인).
