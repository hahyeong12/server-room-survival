## 실제 원인과 최소 수정

집중 창은 실제 `SimulatorApp.make_list()`를 사용합니다. 수정 전 목록에는 기존 한 줄 바인딩을 동일하게 붙여 비교했으며, 수정 후 세 목록은 같은 공통 함수를 그대로 사용했습니다. `tutorial/story/free` 표시는 공통 목록의 fixture 이름으로, 이 창에서 각 게임을 플레이한 것은 아닙니다. 실제 모드별 갱신 회귀는 별도 기존 GUI 테스트로 확인했습니다.

| 항목 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 실제 bindtags | `(위젯 경로, Treeview, ., all)` | 동일 |
| 위젯 MouseWheel | `tree.yview_scroll(-int(e.delta/120), 'units')` | 없음 |
| Treeview 클래스 MouseWheel | `%W yview scroll [expr {-%D / 120}] units` | 그대로 사용 |
| 실제 입력 -120 한 번 | 위젯과 클래스가 각각 1행 이동 | 클래스만 1행 이동 |
| 5행 탐색 | `1→3→5`, 인접 행 건너뜀 | `1→2→3→4→5→4→3→2→1` |
| 선택 고객 | 휠로 선택3 유지 | 선택3 유지 |

계측용 bindtag를 위젯 앞·클래스 앞·클래스 뒤에 끼워 **반환값과 기존 이벤트 처리를 바꾸지 않고** delta·yview·모든 행 bbox·선택·focus를 기록했습니다. 초기 fixture의 레이아웃 전 `height=1` 표본은 실제 입력 결과와 구분하며, 입력 전후 표본의 뷰포트는 58px입니다.

| 네이티브 입력 | Tk 수신 delta | 위젯 처리 뒤 yview | 클래스 처리 뒤 yview |
| --- | --- | --- | --- |
| 수정 전 -120 #1 | -120 | `(0.2,0.4)` | `(0.4,0.6)` |
| 수정 전 -120 #2 | -120 | `(0.6,0.8)` | `(0.8,1.0)` |
| 수정 전 +60 #1 | 이벤트 없음 | 변화 없음 | 변화 없음 |
| 수정 전 +60 #2 | **+120** | `(0.6,0.8)` | `(0.4,0.6)` |
| 수정 후 -120 #1 | -120 | 변화 없음 | `(0.2,0.4)` |

**이중 바인딩이 두 행 이동을 일으킨 것을 실제 입력으로 확인했습니다.** +60 두 번이 +120 한 이벤트로 전달된 것도 이번에는 계측했습니다. 따라서 이전 QA의 Tcl 산술만으로 +60을 한 행 이동으로 판단한 방법은 네이티브 전달 동작을 반영하지 못했습니다. 이번 QA는 delta를 표준 ±120으로 복귀시켰으며, 게임에서 중복 처리를 제거한 뒤 통과 여부를 판정했습니다.

## 첫 전체 실행: 휠 통과·미국 진입 순서 중단

전체 실행은 집중 입력 검사가 통과한 JSON을 필수 인자로 받아야 시작하도록 했습니다. Preflight·입력 직전 전경/가림/좌표 소유 검사·실제 스크린 캡처를 재사용했습니다. 첫 실행은 **136 PASS / 0 FAIL + AbortQA 1건**, 97클릭이며, 개별 assertion의 0 FAIL을 전체 성공으로 해석하지 않습니다.

- 제1장 SG→JP→US를 실제 마우스로 재완주했습니다. 세 고객 모두 고성능 30분·100점, 매번 전량 반환 후 다음 접수, 최종 가용 10/10입니다.
- 결과창의 [제2장 — 한정된 자원 · 시작]을 눌러 **같은 임시 정규 슬롯**에 진입했습니다. 연습 모드나 엔진 직접 호출로 장을 열지 않았습니다.
- 10:30에 접수된 일본·미국 두 행을 실제 휠로 찾아 요청서를 열었습니다. GPU/전력 타일·허용 모드·기한·본문 네트워크 수치를 확인했고, 두 요청서 열람이 저장됐습니다.
- 일본 배정안 3개를 실제 선택·비교했습니다. 미국 절약형이 들어갈 수 있는 안을 선택해 **A GPU3/전력4 + B GPU1/전력1**로 실제 시작했습니다. 가용 6/5, 시각 10:30·진행 0%입니다.
- 미국을 선택한 뒤 현재 고성능의 전력 요구 6이 가용 5보다 커 메인 [배정 설정·선택]이 비활성화됐습니다. QA가 설정창 안에서 절약형으로 바꾸려다가 창을 열지 못해 안전 중단했습니다. **게임 미션 실패와 별개인 자동화 순서 결함**입니다. [당시 화면](screenshots/attempt1_abort.png)

QA를 보완해 미국의 메인 절약형 라디오 버튼을 실제 클릭한 뒤 설정창에 들어가도록 했습니다. 게임 동작은 바꾸지 않았습니다. 별도 Tk 회귀 검사로 이 순서의 실제 위젯 연결과 동시 점유 8/8을 확인했습니다.

처음 정한 추가 실행 조건은 환경 문제에 한정돼 있었으므로, 이 중단을 환경 문제로 간주해 자동 재실행하지 않았습니다. 자동화 순서 결함과 보완·집중 검사 결과를 설명하고 **사용자의 ‘추가 전체 플레이 1회 허용’ 응답을 받은 뒤에만** 최종 실행했습니다. 세 번째 전체 플레이는 하지 않았습니다.

## 최종 실제 플레이 결과

슬롯은 0부터 표기한 실제 원장입니다. 일본 1·2안은 미국 절약형 가능, 3안은 불가였습니다. 최종 선택한 일본 1안은 A에 GPU3/전력4, B에 GPU1/전력1을 두어 B/C에 미국의 GPU·전력을 함께 묶을 공간을 남겼습니다. 조회·모드 선택·배정안 선택만으로는 자원이 점유되지 않았고, 최종 시작 버튼 뒤의 슬롯/전력이 선택안과 일치했습니다.

미국은 메인 절약형을 먼저 선택해 설정창에 들어갔습니다. 이후 창 안에서 **고성능을 실제 선택해 전력 부족·배정안0개·시작 비활성**을 확인하고, 허용된 절약형으로 돌아와 1안을 선택·시작했습니다. 고성능이 처리 시간상 기한 내 가능하다는 초록 배지와 자원 부족이라는 빨간 시작 차단은 서로 다른 조건입니다. 실제 시작은 허용된 절약형만 사용했고, 고객 조건 불변·협의 기록 없음도 확인했습니다.
