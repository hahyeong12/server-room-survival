## 실제 진행과 중단 원인

1. 검증된 제1장 자동 플레이로 세 고객을 실제 처리했습니다. 세 건 모두 고성능·30분·100점·기한 내 완료, 각 완료 후 전량 반환, 최종 가용 10/10을 확인했습니다.
2. [제1장 성공 결과](screenshots/15_success.png)에서 제2장 버튼을 눌렀습니다. **10:30에 일본·미국 요청이 함께 접수**됐으며, 정규 모드·같은 임시 슬롯·신규 시나리오 `ch2_jp`/`ch2_us_v2`를 읽기 전용으로 확인했습니다.
3. 선배 브리핑 5쪽을 실제 다음 버튼으로 읽고 [두 고객 조건 비교](screenshots/16_comparison.png)를 캡처했습니다. **[브리핑 확인] → [확인 · 다음 목표]**까지 클릭했습니다.
4. 요청함 하단으로 휠 이동 후 일본 요청 행을 찾으려 했지만, 한 칸씩 위로 움직인다는 QA 가정이 맞지 않아 12회 탐색 한도에서 안전 중단했습니다. 추가 실행도 같은 결과였습니다. [두 번째 실행의 중단 화면](screenshots/17_abort_state.png)에서 제2장 목표는 요청서 확인이고, 작업은 시작되지 않았습니다.

**C2-QA-01 · 자동화 결함:** `main.py:make_list()`의 위젯 `<MouseWheel>` 바인딩은 `-int(delta/120)`만큼 이동하며 이벤트 전파를 중단하지 않습니다. 설치된 Tk 8.6의 `ttk/utils.tcl`에 있는 `TtkScrollable` 클래스 바인딩도 `expr {-delta / 120}`만큼 이동합니다. 따라서 `delta=120` 한 번에 두 행을 이동합니다. 요청함이 한 행만 보일 때 인접 행을 건너뛰는 탐색이 가능합니다. 첫 실행에는 행별 yview/bbox 이력을 남기지 않아 각 순간의 행 위치까지 재구성할 수는 없습니다. 이는 **게임 미션 실패와 별개인 QA 탐색 실패**입니다.

첫 실행 뒤 QA만 보완해 `delta=60`을 시도하고 행별 bbox·뷰포트 높이·선택·yview를 기록했습니다. Tcl 산술상 위젯 0행·클래스 -1행이라는 계산은 통과했지만 **실제 재실행에서는 한 행 이동에 실패했습니다.** 두 번째 원본 JSON의 `chapter2.row_access`에는 다음 실측이 남아 있습니다.

| 표본 | yview | 실제 보이는 행 | 일본 요청 4의 bbox |
| --- | --- | --- | --- |
| 하단 이동 직후 / +60 첫 입력 후 | 0.8 / 0.8 | 미국 5 | 없음 |
| +60 두 번째 / 세 번째 입력 후 | 0.4 / 0.4 | 이전 미국 3 | 없음 |
| +60 네 번째 이후 | 0.0 / 0.0 | 이전 싱가포르 1 | 없음 |

각 표본의 요청함 높이는 **58px**, 보이는 행 bbox는 `(2,29,210,29)`였습니다. 선택은 계속 일본 `4`였지만 그 행을 실제 노출하지 못했습니다. **+60 입력 두 번에 한 번씩 두 행 이동**한 것이 관측 사실입니다. 네이티브 입력 계층의 휠 누적 가능성은 추론이며, 이 실행에서는 OS→Tk 전달 delta를 별도로 계측하지 않았습니다. 따라서 Tcl 산술 self-check만으로 실제 입력이 교정됐다고 판단한 것은 부정확했습니다.

**QA 행 접근 보완은 해결되지 않았습니다.** 스크립트 첫머리와 해당 입력 위치에도 이 한계를 표시했습니다. 행 전체 노출·입력 직전 소유 검사를 유지했고, 보이지 않는 위치를 추측해 클릭하거나 상태를 바꾸지 않았습니다. 사용자에게 자동화 결함임을 설명한 뒤 추가 1회 예외 승인을 받아 재실행했으며, 추가 승인을 반복 요청하거나 세 번째 실행을 하지 않았습니다. 다음 확인은 실제 Tk 입력 delta/바인딩 계측과 행 접근 방식 검토이며, 이번에는 더 실행하지 않았습니다.
